# Upstream Intel backend audit - 2026-09-30

## Scope and snapshot

This report freezes the upgrade review at ggml-org/llama.cpp master `19e28a27702117d8f2eb16b825b9a308111f67d9` (master commit dated 2026-09-29), the latest commit available within the requested 2026-09-30 cutoff. Do not treat commits after this SHA as part of this audit.

The comparison target is `cpntodd/Oddly-llama.cpp` branch `testing`, checked out locally as `upstream-selective-test-20260929` at `75e6c3298ed043f0c03c417aae4d3d00d313ef7e`. The local branch and `fork/testing` matched at review time. Upstream has 660 commits beyond that branch overall. The backend paths contain 36 upstream-only SYCL commits, 6 OpenVINO commits, and 57 Vulkan commits. These counts include commits already ported with different hashes and commits that only touch tests or other platforms; they are a review inventory, not 99 proposed cherry-picks.

There is no standalone `ggml-xpu` directory in this upstream snapshot. Intel XPU work for the Arc B580 is represented mainly by the SYCL/oneDNN backend and Intel-specific Vulkan paths. OpenVINO GPU execution is a separate path and should be judged separately from OpenVINO NPU work.

The installed model set used to judge relevance includes Gemma 4 E2B Q4_K_XL/Q8_K_XL, Gemma 4 12B Q4_K_XL, Qwen3.5 9B Q4_K_M, PTQ1_0/PQ2_0 Ternary Bonsai 2, plus image and multimodal GGUFs. There is no known DeepSeek-V4/GLM sparse-attention or Qwen4Exp model in the inventory. The exact IQ3_S and IQ4_XS model formats are not represented by the listed models.

## Intel XPU scope

For this machine, "Intel XPU" means the Arc B580 running through SYCL/oneDNN or through Vulkan; it is not a third backend alongside those two. SYCL may select Level Zero as its runtime plugin. The optional direct Level Zero allocator is a separate switch and should not be inferred to be enabled from SYCL support alone. The fork carries its Level Zero header/build integration (`3ed196b97`), SYCL BMG quantized-KV path, and Intel Vulkan Xe Flash Attention/cooperative-matrix work. OpenVINO GPU is tracked separately; OpenVINO NPU support upstream does not imply a B580 GPU feature. The remaining Intel-specific checks are the SYCL in-place F16 KV path and device-context handling for pinned memory, plus B580 validation of generic Vulkan correctness fixes. There is no current evidence that a standalone XPU backend should be added.

## Summary

Several material changes are already on `testing`: SYCL scratchpad/unsupported-op handling, wide FWHT, BMG quantized-KV tiling, SSM-convolution/SiLU fusion and MKL Flash Attention softmax coalescing; Vulkan Intel Xe Flash Attention, Intel cooperative-matrix F16-B matmul, descriptor reuse, cache-view matmul stride handling and aligned F32 loads; OpenVINO SDK 2026.4, unaligned-stride guard, Gemma4 SWA/cache geometry, Qwen3.5 GatedDeltaNet head handling, and a Gemma4 stateful-cache shape adaptation.

The highest-value remaining work is not a bulk upstream merge:

1. Finish the OpenVINO 2026.3.1 feature audit around Qwen3.5, model memory, recurrent-state rollback, operator coverage, and the coordinated stateful/GPU-MoE changes. Existing Gemma4 stateful Q4/Q8 results are short functional smokes, not long-context or performance qualification.
2. Compare and test SYCL oneDNN in-place F16 KV binding and the newer fusion work on actual B580 model graphs. Check large-K `TOP_K` only if it appears in supported model graphs. The DSV4-specific paths remain gated on a suitable model.
3. Review Vulkan convolution alignment as a correctness candidate, then type-aligned `GET_ROWS` and build compatibility. These can be checked with operator/build coverage without waiting for a new model.
4. Revisit format-specific Vulkan IQ4_XS/IQ3_S matmul only if the user adds matching models. The current model list does not justify prioritizing those specialized kernels.
5. Keep the two rejected B580 Vulkan heuristics out of the upgrade queue unless new measurements contradict the recorded results: GDN tuning was shape-sensitive and lacked an end-to-end gain; the MoE-aware tile picker was materially slower on the measured synthetic routed matmul.

## Streamlined upgrade process for this snapshot

Use the pinned upstream SHA in this report as the sole source snapshot for this upgrade batch. The `testing` branch should advance only for rows marked as implementation candidates after their local-equivalence review. Each candidate should have one focused comparison record: upstream SHA, local source counterpart, B580 operator correctness, the smallest relevant model smoke, and before/after timings where the change is a performance optimization. Keep deferred model-specific changes in the table rather than repeatedly polling GitHub for them. Start a new upstream audit only when explicitly moving the cutoff beyond `19e28a277`.

No implementation code or tests were changed or run to produce this report. The tracked source at the review target was clean; the workspace has generated/untracked `codegraph-cache` artifacts that are outside this audit.
